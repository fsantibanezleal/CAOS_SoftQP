The numbered PowerShell and Bash entrypoints dispatch to the same standard-library workflow.py and a product-specific
workflow.json. The flat setup, precompute and dev commands use the same helper. Source identity includes the active
configuration, VERSION, product metadata, API contract, recursive pinned requirements, producer/validator modules,
contract schemas/catalog and exact historical input bytes. These identities serve local artifact admission; they do
not turn a development build into a qualified scientific release.

## External environments and processes

Initialization requires an absolute external CAOS_VENVS_ROOT. The namespace softqp owns .venv-local, optional .venv-api
and optional .venv-lessons. Names must be portable single components. Internal paths, redirected namespace/runtime
directories, non-directory targets and conflicting repository aliases are refused before writes or installation.
Existing historical study/notebook environments remain distinct. Runtime lookup is read-only. Initialization preserves
an existing .env literally, provisions only applicable runtimes, and stamps recursive requirement/lock fingerprints
only after successful installation. Frontend dependencies remain locked; the API is explicitly dormant.

Development requires initialized runtimes and current compact artifacts. It checks free loopback ports before launching
owned frontend/API process groups, propagates child failures, and cleans up only recorded descendants. Its frontend-only
CAOS_DATA_ROOT overlay selects compact committed data. Global raw/model/temp settings remain unchanged for generation,
an active API and the caller.

## Domain generation and admission

Generation creates a fresh stage below external CAOS_TEMP_ROOT. The real SoftQP domain adapter solves the authored
fifteen-case matrix. It does not execute either registered timing study. The existing six historical experiment exports
are staged byte for byte and bound to source identity; changing source or staged bytes is a refusal. No learned model
slot is declared. The complete canonical matrix has four methods per case: lifted, generalized, asymmetric and DAQP.
FlexQP and ElastiQP remain part of the separate complete historical six-method scientific campaign.

Admission requires fifteen distinct case IDs, every canonical matrix method exactly once, checksums/schema validity,
method-specific successful statuses and consistent result identities. A complete replay cannot contain failed matrix
cells or false index flags. Explicit incompatible cells retain a reason and null result. The complete historical
campaign is independently verified, and its staged inputs must match the original source bytes.

The readiness inventory matches the actual catalog minus its declared self-row exclusion. The API and three coupled
exchange rows have explicit missing states, recomputed by the real readiness validator. Coupled JSON placed in the data
root cannot invent a deployed adapter. All undeclared missing/partial outcomes are refused. Offline coupled evidence
and the public SDK0.2 remain separate from this SDK0.1 authored replay and bounded local-edit flow.

## Explicit local promotion

Only --release/-Release requests canonical artifact replacement. The helper parses and hashes one receipt snapshot,
then binds its original source, metadata and payload identities through validators, incoming copies and installation.
A mutable stage cannot substitute for the admitted snapshot. Source or payload mutation at any boundary is a refusal.
Prepared backups support rollback across every owned target; incomplete restoration preserves recovery trees and reports
both original and restoration errors. Concurrent source/metadata edits are preserved. Only data/derived is promoted;
raw journals, checkpoints, manuscript builds and temporary process records remain external.

Independent adversaries cover late validator/source/metadata/receipt changes, matching stage-and-installed tampering,
read-window receipt mutation, namespace/runtime junction redirection, unsafe names, incomplete matrix cells, false backend
states, owned-process cleanup and shell exit forwarding. Actual build, full browser matrix, publication, deployment and
scientific qualification retain their own observed acceptance records.
